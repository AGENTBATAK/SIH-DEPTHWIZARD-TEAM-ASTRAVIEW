# DepthWizard — Current Three.js Architecture Audit

## Scope

This is an audit of the existing React Three Fiber implementation. It describes the current visual prototype and does not claim that its terrain is a scientific DSM renderer.

## Renderer creation and canvas ownership

There are two React Three Fiber canvases, both guarded by `WebGLGate`:

| Canvas | Owner | Role |
|---|---|---|
| Hero/prologue stage | `frontend/three/terrain/StageCanvas.tsx` | Fixed full-viewport, non-interactive cinematic stage shared by the orbit-to-terrain prologue and landing hero. |
| Terrain explorer | `frontend/three/terrain/TerrainViewer.tsx` | Embedded narrative viewer or full-screen `/explorer` instrument. |

The explorer configures a capped DPR (`[1, 1.8]`, lower on coarse pointers), opaque high-performance WebGL, antialiasing, no stencil buffer, and a close-range perspective camera. The stage uses DPR `[1, 2]`, high-performance WebGL, and disables React Three Fiber events because it is not interactive.

`WebGLGate` probes WebGL once. If unavailable, `StaticTerrainFallback` draws the same current height field into a 2D canvas using hillshade, hypsometric colour, and contours.

## Scene and camera creation

### Explorer

`TerrainViewer` renders `ExplorerScene`, which establishes a dark background and fog, then mounts the terrain surface, structures, measurement layer, cursor reticle, particles, interaction controller, flythrough controller, and `OrbitControls` when orbit mode is active.

The default orbit pose is a perspective camera looking at the terrain centre. `CameraDirector` interpolates between orbit and flythrough poses inside `useFrame`, so camera handoff and terrain animation use the renderer clock.

### Prologue and hero

`StageCanvas` renders `StageScene`. `StageCamera` drives the camera from scroll-derived descent state during the prologue, then transitions to a slow hero orbit with eased pointer parallax. `DescentDriver` provides one shared descent state to the globe/space scene and terrain assembly, keeping the visual sequence synchronized.

## Terrain geometry and data

`TerrainSurface` receives `TerrainData` from the Zustand scene store. It does not generate the source terrain itself.

- The source terrain is a normalized square field with an `extentMeters`, height range, structures, and geographic bounds.
- `createHeightTexture()` converts its elevations to a GPU height texture.
- A plane geometry is displaced in the vertex shader. At exaggeration `1`, one world Y unit maps back to the terrain's configured metre extent.
- Multiple prebuilt plane geometries provide distance-based LOD. The current segment levels are 95, 191, 383, and 511, with threshold hysteresis to avoid LOD thrashing.
- A coarser wireframe plane is used when that layer is enabled.

The demo's 1024-square height field is generated by prototype utilities before it reaches Three.js. The renderer samples it; it must not be described as generating real elevation.

## Materials, textures, and lighting

`frontend/three/terrain/terrainMaterial.ts` creates custom `ShaderMaterial` instances.

- The vertex shader samples the height texture, displaces the terrain, and recomputes normals by central differences.
- The fragment shader mixes RGB context and a colour-ramp LUT; it applies directional/sky/rim lighting, elevation contours, a coordinate grid, fog, cursor highlighting, and optional scanlines.
- The source image is loaded with `TextureLoader`; its image URL is the scene preview or generated demo plate.
- The colour-ramp LUT and height texture are regenerated when their source inputs change.
- The prologue loads `frontend/public/textures/earth-color.webp` and `earth-clouds.webp` for the space sequence.

## Interaction and controls

- `OrbitControls` handles damped orbit navigation in normal explorer mode.
- `TerrainInteraction` raycasts the terrain for hover, inspection, and two-point measurement.
- `TerrainControls` changes existing display layers, ramp, and exaggeration through the Zustand store.
- `FlythroughController` uses an in-frame first-person controller: keyboard/touch movement, pointer-lock mouse look with fallback, terrain-following altitude, footprint bounds, and periodic HUD readouts.
- `MapPanel` is lazily loaded and provides the existing non-WebGL 2D map mode.

## Animation loop and React ↔ Three.js communication

React owns composition and durable application state. React Three Fiber owns the render loop.

| Direction | Current mechanism |
|---|---|
| React → Three | `TerrainViewer`, `StageCanvas`, and `TerrainSurface` select terrain, layers, exaggeration, ramp, scene image, and camera mode from Zustand; props and shader uniforms receive those values. |
| Per-frame updates | `useFrame` updates camera motion, flythrough position/readout, terrain time/rise/opacity uniforms, LOD selection, prologue descent, and hero orbit. |
| Three → React | Hover/pick handlers update Zustand cursor, measurement, and selected-structure state; the flythrough sends a throttled readout to local UI state. |
| Scroll → Three | The prologue's external stage state is subscribed to with `useSyncExternalStore`; `DescentDriver` reads it each frame. |

Refs carry high-frequency values such as terrain rise, opacity, camera transition, and motion state so those values do not require React renders at frame rate.

## Resize handling

Canvas sizing and camera aspect updates are handled by React Three Fiber. The prologue uses `useThree().viewport.aspect` when calculating its descent camera state, allowing the same curve to adapt to viewport shape. Explorer layout is CSS-sized using `svh` and its containing element; the browser Fullscreen API controls full-screen mode.

## Resource lifecycle and cleanup

- React Three Fiber owns canvas lifecycle and removes mounted scene objects when their components unmount.
- `TerrainSurface` disposes the height texture, LUT texture, shader materials, LOD geometries, and wire geometry in an effect cleanup.
- `FlythroughController` unregisters keyboard, mouse, and pointer-lock listeners and exits pointer lock on cleanup.
- `TerrainViewer` unregisters fullscreen listeners on unmount.
- `WebGLGate` releases its one-off support-probe context through `WEBGL_lose_context` when the extension is available.

This audit does not change resource behavior.

## Current performance risks intentionally not changed in Phase 1

1. The canonical demo contains a 1024-square height field; although the surface uses LOD and GPU displacement, its CPU-generated raster products, JSON transport for persisted scenes, and texture allocation are material work on lower-end devices.
2. The hero/prologue and explorer are different canvases. They are used in different UI contexts, but a future audit should confirm no accidental overlapping canvas lifecycle occurs during route or scroll transitions.
3. Per-frame flythrough logic performs terrain sampling and state/readout work. The readout is throttled, but future real DSM sizes need measurement and sampling budgets.
4. Loaded RGB preview textures and source image sizes depend on user input and could stress GPU memory; the current upload path creates a bounded display preview, but real artifacts need explicit texture policy.
5. A single plane is suitable for the current square demonstration terrain. Tiled DSM visualization, culling, streaming, and large-raster coordinate handling are future work.
6. MapLibre, Three.js, GeoTIFF utilities, and the animation libraries are substantial browser dependencies. No dependency, code-splitting, or rendering optimization was added in this phase.

## Future visualization boundary

```text
Authoritative backend DSM + metadata
        ↓
Visualization payload adapter
        ↓
TerrainData-compatible height grid / tiles + texture context
        ↓
TerrainSurface and explorer controls
```

Future payloads must preserve units, geographic metadata, valid-data masks, and provenance. Any display normalization belongs at the adapter/renderer boundary and must not overwrite the authoritative DSM values used for measurements or export.

## Phase 3 lifecycle and allocation improvements

### Before

- The renderer lifecycle was already React Three Fiber-managed: two canvas definitions exist (stage and explorer), with the normal page flow mounting one WebGL canvas at a time.
- Explorer DPR was already capped at 1.8 (1.3 on coarse pointers); stage DPR was already capped at 2. Neither canvas configured shadows or tone mapping, and both use opaque antialiased high-performance WebGL contexts.
- Terrain geometry, height texture, LUT, custom materials, LOD geometries, particles, globe resources, event listeners, and pointer lock already had component cleanup paths.
- The terrain interaction path coalesced pointer moves to one ray-march per animation frame, but allocated a `Vector2` and `Raycaster` for every executed pick.
- The flythrough controller allocated one `Vector3` acceleration object every frame while it was enabled.

### After

- `TerrainInteraction` owns one memoized NDC vector and raycaster for its mounted lifetime. Pointer events still coalesce exactly as before, and the raycast algorithm, hit testing, measurement, inspection, and controls are unchanged.
- `FlythroughController` owns one memoized acceleration vector and resets/reuses it each frame. Movement, terrain following, pointer lock, keyboard/touch controls, and HUD values are unchanged.
- React Three Fiber remains the only render-loop owner. No manual renderer, animation loop, resize listener, or controls instance was added.

These changes remove avoidable garbage collection pressure from the two hot paths without changing terrain geometry, material uniforms, LOD, visual quality, render resolution, camera behavior, or UI state.

### Measured checks

The existing `npm run perf:demo` browser check completed before and after the changes with the canonical 1024² demo terrain, one canvas, zero captured console errors, and zero recorded long tasks in that scenario. FPS, GPU memory, renderer object counts, and texture counts were not measured.

The development-server log continues to show an upstream `THREE.Clock` deprecation warning. The project source does not create a `THREE.Clock`; dependency changes are intentionally out of scope for this performance phase.
