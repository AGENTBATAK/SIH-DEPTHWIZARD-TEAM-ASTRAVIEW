# DepthWizard — Technical Judge Q&A

## Q1. Why Depth Anything V2?

Depth Anything V2 provides a strong pretrained monocular depth-estimation foundation. It allows the project to estimate scene depth from RGB imagery and provides the starting point for the relative-depth stage.

## Q2. Does Depth Anything V2 directly produce elevation in meters?

Not by default. The architecture treats its output as relative depth and uses a separate metric calibration stage against suitable reference/control data.

## Q3. Why is the 75° viewing angle important?

The target imagery has a specific overhead viewing geometry. Model behavior can change with camera orientation, object appearance, scale and occlusion. Therefore the pipeline explicitly validates and tunes the model for the target domain instead of assuming generic performance.

## Q4. What is the role of GIS?

GIS provides spatial reference and ensures that imagery, reference elevation and predicted elevation are aligned in the same coordinate system and raster grid.

## Q5. Why do you need calibration?

Relative depth does not establish a physical elevation scale. Calibration maps model output to a metric reference.

## Q6. What is the difference between DEM and DSM?

A DSM represents visible surface elevation, including buildings and vegetation. A bare-earth DEM attempts to represent terrain without above-ground objects. DepthWizard's primary product is a DSM.

## Q7. Why use Three.js?

Three.js provides browser-based WebGL visualization. It converts the processed elevation grid into an interactive 3D terrain surface for inspection and flythrough.

## Q8. Does Three.js generate the elevation data?

No. Three.js visualizes the DSM generated by the backend scientific pipeline.

## Q9. How do you measure accuracy?

Where reliable reference data is available, the system compares predicted elevation with reference elevation using MAE, RMSE, R² and spatial error analysis.

## Q10. What happens when there is no reference DEM or GCP?

The system can still generate a relative-depth visualization, but it must not present that output as validated absolute elevation. Metric claims require appropriate calibration/reference information.

## Q11. How do you process large images?

Large images are tiled with controlled overlap. Predictions are blended/reconstructed into a continuous raster before calibration and DSM generation.

## Q12. How do you handle CRS?

The system reads available CRS metadata, validates it, selects a common working CRS and reprojects datasets before spatial comparison or raster alignment.

## Q13. How do you prevent tile seams?

Use overlapping tiles and a consistent reconstruction/blending strategy. Seam artifacts are also checked during post-processing and validation.

## Q14. What happens if GPU memory is insufficient?

The worker can reduce tile/batch size and retry while maintaining the same processing contract.

## Q15. How is the system reproducible?

Each job records the source input, model version, preprocessing configuration, reference dataset, calibration method and output metadata.

## Q16. What are the main limitations?

Accuracy depends on image quality, viewing geometry, scene content, reference quality, calibration and model generalization. The prototype should therefore report measured performance rather than claim universal accuracy.

## Q17. What makes the architecture modular?

ML inference, GIS processing, calibration, DSM generation, validation and visualization are separated into independent modules connected through defined data contracts.

## Q18. What would you improve next?

Potential next steps include a larger representative dataset, systematic domain adaptation, stronger uncertainty estimation, multi-view/stereo integration where available, scalable GPU workers and more extensive field validation.
